# Синхронизация Gradebook v14

## Почему заменён прежний алгоритм

В v13 выбирался целый снимок базы по `updatedAt`. Сценарий: два человека скачали
один снимок, первый поставил оценку студенту А, второй студенту Б. Более поздний
снимок мог заменить первую оценку. Архив снимков облегчает восстановление, но не
объединяет такие правки и не устраняет гонку «прочитал — заменил файл».

В v14 единица обмена — неизменяемый пакет операций. Независимые поля объединяются,
конкурентные значения одного поля сохраняются для ручного решения. Не используются
часы компьютера для выбора победителя.

Это собственная компактная реализация регистра с несколькими значениями и векторами
версий, а не встроенная библиотека Automerge/Yjs и не полная реализация их протоколов.
Выбор сохраняет автономный HTML без внешних скриптов, WASM, CDN и зависимостей времени
выполнения. Нет совместного посимвольного редактора, CRDT-последовательностей и
автоматического объединения элементов массивов. Сложные поля остаются атомарными;
при разных правках пользователь выбирает целый вариант.

## Идентичность и причинность

- Вкладка при каждом запуске создаёт случайный `actor`. Даже копия браузерного профиля
  не переиспользует счётчик другого работающего клиента.
- Операция: `id = actor:seq`, `context = {actor: последний увиденный seq}`, автор,
  время для истории и изменения полей. Время не влияет на объединение.
- Ключ поля: JSON-массив `[table, recordId, field]`. Для результатов `recordId` —
  JSON-пара `[studentId, lessonId]`; для рассадки — её логическая область.
- Существование записи хранится в `$exists`. Удаление — значение `false`, а не
  исчезновение информации из истории. Изменение дочерней записи также подтверждает
  существование её родителей, чтобы спор об удалении не спрятал новую оценку.
- Запись B заменяет A, только если вектор B включает A. При отсутствии причинного
  порядка сохраняются обе. Чтение выбирает вариант по идентификатору операции,
  одинаково на всех репликах. Разные значения попадают в список конфликтов.
- Выбор значения создаёт новую операцию, учитывающую все известные варианты.
  Конкурирующее ещё не полученное решение не считается автоматически проигравшим.

Применение пакетов идемпотентно, порядок доставки не влияет на результат при одном
наборе операций. Проверяются схема, ключи, повторные ID с другим содержимым, цепочки
счётчиков и причинные зависимости. Пакет с недостающими зависимостями не помечается
полученным: следующий обмен повторит чтение списка.

## Доставка через Диск

1. Сохранение формы вычисляет разницу с базой этой вкладки, объединяет уже записанные
   операции других вкладок и добавляет свою операцию.
2. Один `localStorage.setItem` сохраняет проекцию базы, операции, подтверждения и
   ещё не подтверждённый пакет. OAuth-токен лежит в отдельной конфигурации.
3. Обмен фиксирует пакет всех неподтверждённых операций под случайным именем.
   До первого сетевого запроса пакет уже записан локально.
4. Пакет загружается с `overwrite=false`. Затем скачивается и сравнивается с
   ожидаемым JSON. Потеря ответа после успешного PUT безопасна: повтор читает тот
   же путь и не создаёт новую операцию.
5. Полный список пакетов читается с пагинацией; скачиваются только неизвестные
   неизменяемые файлы. Общий перезаписываемый манифест не используется.
6. Полученные операции проверяются на отдельной реплике. Если за время обмена
   пользователь начал/сохранил правки, полученный набор пока не применяется, а
   локальная очередь сохраняется. Следующая попытка завершает объединение.
7. Объединённая база, история и подтверждения сохраняются локально. Изменение,
   появившееся на Диске после чтения списка, будет получено в следующем обмене.

Сходимость предполагает последующие успешные обмены после окончания параллельных
записей и доступность всех неизменяемых пакетов. Один обмен не может гарантировать,
что другой компьютер не отправит ещё один пакет сразу после завершения чтения.
При автосинхронизации получение повторяется раз в 60 секунд, после локального
сохранения и при событии восстановления сети.

Нет удаления истории/компактации: безопасное удаление потребовало бы учитывать
давно не подключавшиеся реплики. Полный список метаданных и локальная история
растут; известные файлы повторно не скачиваются. Лимит `localStorage` зависит от
браузера. При ошибке записи приложение сообщает об этом и предлагает экспорт.

## Аккаунты и пределы защиты

Идентификатор аккаунта — SHA-256 нормализованного логина. Файл аккаунта создаётся
без перезаписи и перечитывается, поэтому одновременная регистрация одного логина
не должна выдавать двум клиентам разные успешные идентичности. Проверочное значение
пароля: PBKDF2-SHA256, случайная соль, 310 000 итераций. Пароль и OAuth-токен не
входят в пакеты журнала. Для офлайн-входа кэшируется проверочное значение аккаунта;
сессия вкладки хранится в `sessionStorage`.

Личный журнал получает пространство по ID аккаунта, общий — по нормализованному
имени. Локальные ключи разделены также по аккаунту, поэтому выход/переключение не
переписывают соседние локальные базы.

Общий токен — полный доступ ко всем ресурсам папки приложения. Пароли не являются
серверным ACL или шифрованием. Любой владелец токена может прочитать/удалить файлы,
а доступ к профилю браузера позволяет прочитать локальную базу. Нет гарантий
против злонамеренного участника, физической потери устройства или ручного удаления
пакетов. Для такой модели угроз нужен иной механизм авторизации и шифрования.

## Проверка

`npm ci --ignore-scripts && npm test` запускает прежние тесты журнала и новые
проверки чистой модели и двух независимых полных экземпляров приложения в jsdom.
Транспорт моделирует API Диска, неизменяемые файлы, пагинацию и ошибки связи.

Проверены независимые оценки/комментарии, одинаковые и разные конкурентные значения,
явное разрешение, удаление против редактирования/новой дочерней записи, обратный
порядок доставки и повторы, три реплики с разными перестановками, перезагрузка,
потеря ответа после PUT, сохранение во время отправки, личные пространства,
переключение аккаунтов, пароли/офлайн-вход и отказ от повреждённого пакета.

Это воспроизводимые проверки с эмуляцией, не испытание реального Яндекс Диска с
пользовательским токеном. Токен пользователя в среде разработки не запрашивался
и не использовался. Реальные ограничения OAuth, CORS, задержки видимости файлов и
квоты необходимо проверять на рабочих устройствах.
